# Swarm skills, hooks, and tasks: runtime model for the Pi port

This document records the deeper Swarm behavior that must survive the Pi
translation. The key finding is that skills and tasks are stateful runtime
systems. They are not just prompt files and convenience tools.

## 1. Skill lifecycle

### Discovery and precedence

Swarm's `skills.Loader` constructs an ordered search path and initializes the
registry in two phases:

1. register embedded built-in skills;
2. load installed-plugin state;
3. discover skills from all search paths;
4. register discovered skills, allowing user-installed entries to shadow
   built-ins with the same name.

Evidence:

- `upstream/swarm-sdk/internal/skills/loader.go:13–25, 36–80`
- `upstream/swarm-sdk/internal/skills/loader.go:83–107`
- `upstream/swarm-sdk/internal/skills/registry.go:16–35, 129–183`

Search paths have policy implications:

```text
managed/policy skills
  → install directory
  → install-directory/skills
  → Claude-compatible user skills/commands
  → ~/.swarm/skills
```

The managed directory is prepended when enabled, so policy skills take
precedence. Autogenerated skills are classified separately even when found
through the broader user directory.

Pi has resource discovery and project/user package scopes, but the Swarm port
must add explicit source classification and closed-mode precedence. A project
skill must not silently override a managed policy skill.

### Skill format and executable support

Each skill is a package centered on `SKILL.md`, optionally containing:

```text
references/
templates/
scripts/
assets/
hooks.json
```

The executable surface matters. `hooks.json` can register command or prompt
hooks for events such as `PreToolUse`, `PostToolUse`, and `SessionStart`.
Scripts and binary assets must be treated as package bytes, not model-generated
text.

Pi's skills and packages provide a compatible loading concept. The adapter
needs to preserve the distinction between:

- instructions injected into the model context;
- executable helpers invoked by a skill;
- extension hooks registered in the host;
- support files that must be copied byte-for-byte.

### On-demand use versus auto-activation

The current Swarm loader retains older activation APIs, but its comments make
the current behavior explicit:

- `Activate` and `Deactivate` are compatibility methods;
- `GetActiveInstructions` and `GetActiveSkills` return no active prompt state;
- `AutoActivate` is a no-op;
- skills are invoked on demand through the skill tool.

Evidence: `upstream/swarm-sdk/internal/skills/loader.go:186–239`.

This means the Pi port should not recreate trigger-based implicit prompt
activation as a second mechanism. Use Pi's on-demand skill/resource model, and
port only the explicit Swarm skill tool and lifecycle accounting.

## 2. Autogenerated skills and curation

### Service modes

`autogenskills.Service` is the top-level lifecycle coordinator. Its contract
defines three modes:

| Mode | Behavior |
|---|---|
| never | all operations are no-ops with no side effects |
| manual | skill creation works, automatic nudges do not |
| auto | metrics, nudges, creation, patching, and curator behavior are active |

Evidence: `upstream/swarm-sdk/internal/skills/autogenskills/service.go:15–24`.

The service tracks turn, tool-call, error, resolved-error, nudge, and
skill-created metrics. It exposes lifecycle hooks, programmatic creation,
patching, viewing, and curator access:

- `RunTurn` updates turn metrics and evaluates nudge thresholds;
- `HandleToolCall` and `HandleError` update outcome metrics;
- `CreateSkill` delegates to the validated factory;
- `PatchSkill` delegates to the version-bumping factory;
- `GetHooks` returns the lifecycle and budget-enforcement hooks.

Evidence: `service.go:61–129, 201–268`.

### Safe mutation rules

The `SkillFactory` is the only supported creation path. It:

- validates options before disk I/O;
- enforces a minimum instruction length when configured;
- refuses to overwrite an existing skill;
- writes directories and files with controlled permissions;
- writes the document atomically;
- registers the new skill immediately;
- increments creation metrics.

Evidence: `upstream/swarm-sdk/internal/skills/autogenskills/factory.go:213–300`.

`SkillManage` adds stronger review controls:

- `view` before mutation when configured;
- pinned skills cannot be modified autonomously;
- preview mode permits only read/review operations;
- archive with consolidation requires support-file parity;
- `absorb_files` is the only safe binary/support-file transfer;
- `history` and `undo` preserve reversible revisions;
- `review` records that no mutation was needed.

Evidence: `upstream/swarm-sdk/internal/skills/autogenskills/skillmanage.go:18–79,
99–150`.

Pi implementation requirement:

```text
swarm-skill-state
  registry/source precedence
  usage and revision metadata
  pinned/stale/archived/consolidated states
  immutable history and undo

swarm-skill-manage
  list/view/read_file/history
  create/patch/write_file/absorb_files
  archive/review/undo
  expected_revision and view-before-write guards
```

Do not implement this as a free-form `write` wrapper. The operation must be
validated and routed through one stateful manager.

### Curator decisions

The curator models skill state as:

```text
active
stale
archived
pinned
consolidated
```

It can recommend:

```text
none
mark_stale
archive
patch
consolidate
```

Evidence: `upstream/swarm-sdk/internal/skills/autogenskills/curator.go:17–70`.

The curator does not mean “automatically rewrite whatever looks similar.”
Pinned entries are protected, archival is recoverable, consolidation must
preserve support files, and the final mutation is a separate guarded action.
Pi should expose curator recommendations as durable state or a review
message, then require the same explicit mutation contract.

### Skill review hook

`LifecycleHook` observes successful and failed tool outcomes but never blocks
tool execution. It:

- counts non-skill calls since the last review;
- resets its counter when a skill is used;
- detects error→resolution patterns;
- gives task completion a higher-value review boundary than arbitrary count
  thresholds;
- asks for patch/umbrella extension/support-file preservation;
- emits a durable reminder through the hook budget.

Evidence: `upstream/swarm-sdk/internal/skills/autogenskills/hook.go:15–25,
44–79, 90–208, 223–278`.

The Pi translation is a `tool_result` observer plus `turn_end`/task-state
integration. It must remain non-blocking. Skill policy errors and
authorization errors belong to the central policy hook, not this reminder
hook.

## 3. Hook topology

Swarm hooks have separate responsibilities and priorities:

```text
session/start and configuration
  ↓
before-agent prompt/context governance
  ↓
permission and steering gates
  ↓
tool invocation
  ↓
tool outcome classification
  ↓
task accounting and skill-review nudges
  ↓
durable audit/persistence
```

The autogen lifecycle hook is priority 91 and explicitly sits below
block-resolution enforcement while competing with task maintenance through a
shared nudge budget. This is a policy relationship, not merely a registration
order.

Pi handlers run in extension/load order, so the port needs a deterministic
coordinator:

```text
swarm-hook-coordinator
  ordered handler list
  event normalization
  shared tool/task/skill classifier
  explicit block/observe/fail behavior
  shared nudge budget
  redacted durable audit
```

Only the coordinator should enforce calls. Skill review, task reminders,
metrics, and UI updates should observe normalized outcomes.

## 4. Task system

### TaskManage is the canonical protocol

Swarm deliberately consolidates task operations behind one structured
`TaskManage` tool. The protocol supports:

- `create`, `update`, `get`, and `list`;
- `sequential` and `atomic` batches;
- operation keys and references;
- parent/child hierarchy;
- `blocks` and `blockedBy` dependencies;
- owner/agent assignment;
- categories such as researching, planning, acting, verifying, debugging,
  and documenting;
- bounded pagination;
- notes and typed note categories;
- optional audit output.

Evidence:

- `upstream/swarm-sdk/internal/tools/ii/task_manage.go:10–115`
- `upstream/swarm-sdk/internal/tools/ii/task_operation.go:11–107`

### Transaction semantics

Sequential mode commits each successful operation and skips the remaining
operations after the first failure. Atomic mode runs against a candidate
manager and commits all changes only if every operation succeeds. On failure:

- previously successful operations are marked rolled back;
- the failing operation returns a structured error;
- later operations are skipped;
- operation-key registrations are not leaked;
- persistence failure rolls the candidate state back.

Evidence: `upstream/swarm-sdk/internal/tools/ii/task_manage.go:197–350`.

This is stronger than a typical todo extension. The Pi port must preserve the
wire-level batch result and transactional behavior even if the TUI is simpler.

### Stable references and persistence

An operation key can resolve a task produced by an earlier operation in the
same batch or a previous `TaskManage` call. Atomic batches defer key
registration until commit. Deletion removes associated key mappings.

The task store also enforces:

- no self-parenting;
- no dependency cycles;
- deterministic sibling ordering;
- dense display numbering;
- idempotent decomposition.

Evidence:

- `upstream/swarm-sdk/internal/tools/ii/task_manage.go:150–191,
  264–324`
- `upstream/swarm-sdk/internal/taskstore/tree.go:20–29, 31–59`

### Hook interaction

Task events are not just UI updates. They feed:

- task enforcement and ownership checks;
- task maintenance reminders;
- task completion skill-review nudges;
- audit records;
- subagent parent/child routing;
- workflow completion signals.

The `TaskManage` adapter should therefore emit a normalized operation event
for every operation, including skipped, failed, rolled-back, and persistence
failure outcomes. A single tool-result string is insufficient for downstream
governance.

## 5. Workflow relationship

Swarm workflows are DAGs of agent groups. Groups specify execution strategy,
agents, provider/model resolution, prompts, tools, and capabilities. The
workflow layer schedules groups in dependency order; it is distinct from the
task tree:

```text
workflow DAG
  orchestrates agent groups and execution phases

task tree
  tracks durable work items, ownership, dependencies, and completion

skill system
  supplies reusable instructions and executable support

hook system
  observes and governs transitions across all three
```

Pi's extension ecosystem has candidates for subagents, plan mode, and
worktrees, but none should be allowed to collapse these three state machines
into one UI abstraction.

## 6. Pi mapping

| Swarm contract | Pi mechanism | Required adapter |
|---|---|---|
| `SKILL.md` instructions | Pi skills/resources | source classification and closed-mode filtering |
| skill support files | Pi package files | byte-preserving install/absorb path |
| skill tool | custom `registerTool` | full `SkillManage` operation schema |
| skill usage tracking | `tool_result` | normalized skill-use event and persisted metadata |
| autogen nudge | `tool_result`, `turn_end` | non-blocking shared-budget reminder |
| curator state | custom session entries | pinned/stale/archive/consolidation state |
| revision/undo | custom entries plus filesystem manager | expected revision and recoverable mutation |
| task tool | custom `registerTool` | exact TaskManage batch protocol |
| task persistence | custom session entries or external store | restart-safe identity and key registry |
| task hooks | `tool_call`, `tool_result`, `turn_end` | centralized event coordinator |
| workflow DAG | custom command/tool or external runner | separate group scheduler and durable results |

## 7. First implementation boundary

The first Pi slice should include the contracts, not the whole feature set:

```text
swarm-runtime-contract.ts
  stable session/tool/task/skill event types

swarm-hook-coordinator.ts
  deterministic observer/gate ordering

swarm-skill-state.ts
  list/view/history/revision metadata

swarm-skill-manage.ts
  guarded operations, initially read/review plus safe local create/patch

swarm-task-manage.ts
  exact schema, sequential/atomic execution, durable key references

swarm-persistence.ts
  append custom entries and rehydrate on session_start
```

Implement the Pi-native Forge read adapter alongside these contracts, but do
not add subagents, MCP, browser tools, or remote bridges until the skill/task
event and persistence invariants are tested.

## Acceptance tests

1. Managed skill precedence survives project/user discovery.
2. On-demand skill invocation records `last_used_at`.
3. A pinned skill cannot be autonomously patched or archived.
4. `absorb_files` preserves support-file bytes exactly.
5. A skill mutation requires the expected revision and, when configured, a
   prior `view`.
6. A curator recommendation can be recorded without mutating the skill.
7. Skill review nudges never block tool execution.
8. A sequential TaskManage batch commits its successful prefix and skips the
   remainder after failure.
9. An atomic TaskManage batch leaves no task, key, or persistence residue after
   rollback.
10. Task references resolve across separate calls only after commit.
11. Parent/dependency cycles are rejected.
12. Task completion emits one normalized event and can trigger a bounded skill
   review reminder.
13. Session restart rehydrates skill metadata, task keys, and policy without
   reusing stale runtime objects.
14. Workflow completion, task completion, and skill review remain distinct
   events.
